몇 달 전에 "이번엔 코드를 한 줄도 안 짜고 AI한테 프로그램을 통째로 맡겨보자"는 생각으로 시작한 사이드 프로젝트가 있습니다. 윈도우용 화면 캡처·편집 프로그램입니다. 외장하드에 처박아뒀던 걸 최근에 다시 꺼내봤는데, 개발 과정을 기록한 대화 로그와 문서가 생각보다 훨씬 많이 남아있어서 정리 겸 후기를 씁니다.

## 왜 만들었나

고객사에 상주하면서 진단 업무를 하다 보면 평소 쓰던 도구를 그대로 못 쓰는 경우가 종종 있습니다. 저는 캡처·주석 작업에 픽픽(PicPick)을 즐겨 쓰는데, 고객사 PC에는 설치가 막혀 있거나 외부 프로그램 반입 자체가 까다로운 환경이 많았습니다. 그렇다고 대체할 만한 다른 캡처 프로그램을 써보면 편집 기능이 빈약하거나 인터페이스가 손에 안 맞아 오히려 불편했고요. 그래서 아예 필요한 기능만 넣은 캡처 프로그램을 직접 만들어서 개인 용도로 쓰기로 했습니다. 다만 이번엔 제가 직접 짜는 게 아니라 Gemini CLI에게 기획부터 구현까지 맡겨보는 게 목적이었습니다.

## 어떻게 만들었나 — PDCA로 코드 짜는 AI

Gemini CLI 확장인 **bkit Vibecoding Kit**을 얹어서 작업했습니다. bkit은 요청을 곧장 코드로 넘기지 않고 Plan(기획) → Design(설계) → Do(구현) → Analysis(설계-구현 갭 분석) → Report(완료 보고) 순서의 PDCA 사이클을 강제합니다. 그래서 `docs/` 폴더 밑에 기능 하나당 기획서·설계서·분석서·보고서가 세트로 쌓입니다.

재밌는 건 팀을 "역할극"으로 꾸릴 수 있다는 점입니다. 실제로 제가 던진 프롬프트는 이랬습니다.

> `/pdca team CTO님은 28년차 시니어 개발자고 현재 프로젝트에 도형삽입이 안되는 문제와 색상 선택이 불가능한 문제 등등 UI/UX 개선작업과 각종 기능 오류 등을 팀을 꾸려서 개선작업을 해야합니다.`

이러면 bkit이 "CTO"·"프론트엔드 아키텍트"·"QA" 같은 페르소나를 가진 서브에이전트를 붙여서 각자 역할대로 계획을 짜고 코드를 고칩니다. 나중엔 `/control level L4`로 자율 모드까지 켜서, 승인 없이 알아서 리팩토링과 빌드를 진행하게 두기도 했습니다.

## 결과물 — 생각보다 커진 스펙

처음엔 "캡처 + 간단한 편집" 정도로 시작했는데, PDCA 사이클을 몇 바퀴 돌리는 동안 스펙이 눈덩이처럼 불어났습니다. 최종적으로 남은 기능 목록은 이렇습니다.

![직접 만든 캡처 프로그램 메인 화면 — 리본 메뉴에 캡처 8종, 파일, 도구 그룹이 정리되어 있다](/도구/images/capture-tool-main-window.png)

- **캡처 8종**: 전체화면 / 영역 지정 / 윈도우 / 윈도우 컨트롤(버튼 단위) / 고정 사각 영역 / 자동 스크롤 / 자유형(폐곡선) / 마지막 캡처 반복
- **에디터**: 펜·도형·화살표·모자이크·텍스트 주석(말풍선 팝업 편집), 스탬프 도구, 화이트보드 모드, 화면자, 색상 피커 + 돋보기
- **인프라**: 멀티 모니터·고DPI 대응(`DwmGetWindowAttribute`로 그림자 영역 제외, DPI별 좌표 보정), 다크/라이트 테마, 설정 파일 손상 시 자동 백업 롤백, 크래시 리포팅

스택은 **.NET 8 WPF + MVVM(CommunityToolkit.Mvvm) + SkiaSharp(렌더링) + Fluent.Ribbon(오피스 스타일 UI)** 조합입니다. AI가 처음부터 이 조합을 골랐고, 이유는 "리본 메뉴 구현 용이성"과 "SkiaSharp의 성능·확장성"이었습니다.

## 실제로는 이랬다 — 대화 로그 발췌

기획서만 보면 다 잘 만들어진 것 같지만, 실제 대화 로그를 다시 훑어보니 훨씬 날것의 과정이 있었습니다.

**시작은 순조로웠습니다.** 첫 사이클은 일치율(Match Rate) 97%로 끝났고, `/pdca team` 한 번으로 캡처 8종과 에디터가 거의 다 구현됐습니다.

**그다음부터 진짜 개발이었습니다.** 도형을 그렸는데 화면에 바로 안 보이고, 다른 도구를 눌러야 그제서야 나타나는 렌더링 버그를 만났습니다.

> 도형 그리면 바로 안보이고 그리기 툴 다른거 누르니까 그제서야 나와요 아잇 도형 편집은 다 한박자씩 느려요

원인은 캔버스 컨트롤이 마우스 이벤트 핸들러에서 `InvalidateVisual()`을 호출하지 않아서였습니다. 텍스트 편집도 비슷한 문제가 있었는데, 텍스트 상자를 클릭하면 텍스트는 그대로고 테두리 배경 바만 늘어나는 버그였습니다 — 배경 바와 텍스트박스를 별개 컨트롤로 관리하다 생긴 동기화 문제였습니다.

PDCA의 "일치율(Match Rate)" 지표를 대하는 제 태도도 재밌었습니다.

> 매칭률 100프로 만들어줘

설계 대비 구현 일치율이라는, 원래는 품질 관리용 숫자를 그냥 게임 점수처럼 올려달라고 요구한 거죠. 지금 보면 이 지표가 실제 완성도를 얼마나 정확히 반영하는지는 따로 검증한 적이 없다는 게 좀 걸립니다.

**빌드는 생각보다 고통스러웠습니다.** `dotnet publish`를 실제로 돌리는 단계에서 흔한 C#/WPF 실수들이 그대로 튀어나왔습니다.

```
error CS0234: 'System.Windows' 네임스페이스에 'Point'이(가) 없습니다
error CS0103: 'newStack' 이름이 현재 컨텍스트에 없습니다
error MC3000: Data at the root level is invalid. (XAML 664번째 줄)
error CS0104: 'Point'은(는) 'System.Drawing.Point' 및 'System.Windows.Point' 사이에 모호한 참조입니다
```

`System.Drawing.Point`와 `System.Windows.Point`를 섞어 쓰다 생긴 모호한 참조 에러, XAML 문법 깨짐, 존재하지 않는 변수 참조까지 — AI가 기능 단위로는 그럴듯한 코드를 빠르게 뽑아내지만, 프로젝트 전체를 한 번에 `dotnet publish`로 검증하기 전까지는 이런 문제들이 계속 숨어있었습니다. 결국 "너가 빌드해", "굽기 해" 같은 재촉을 몇 번 더 거친 뒤에야 에러 없는 빌드가 나왔습니다.

## 배포까지는 갔다

최종적으로는 `dotnet publish`로 self-contained 단일 실행 파일을 뽑고, 자체 서명 인증서로 코드 사인한 뒤 MSIX 패키지(v1.0.0)와 exe 설치 파일(v1.0.1)까지 만들었습니다. "설치하려면 뭐 실행해야 해?"로 시작한 프로젝트가 실제로 더블클릭 설치 가능한 상태까지는 도달한 셈입니다.

## 보안 점검 에피소드 — AI가 준 100점을 믿어도 될까

마지막에는 AI에게 보안 감사를 시켰습니다. 결과 보고서는 이랬습니다.

| 항목 | 결과 |
| :--- | :--- |
| RCE (원격 코드 실행) | 위험 없음 — 쉘 명령 호출 로직 없음 |
| 버퍼 오버플로우 | 위험 없음 — `unsafe` 코드 미사용, SkiaSharp 관리형 API만 사용 |
| 정보 유출 | 위험 없음 — 네트워크 모듈(HttpClient, Socket) 자체가 없음 |
| 역직렬화 취약점 | 위험 없음 — `System.Text.Json` 사용, `BinaryFormatter` 미사용 |
| 경로 조작 | 위험 없음 — 저장 경로 화이트리스트 검증 |

**종합 결과: 100% (보안 결함 없음).**

평소 진단 업무를 하는 입장에서는 이 100점을 그대로 믿기가 좀 망설여집니다. 실제로 한 건 정적 분석 수준의 자체 점검이고, 퍼징이나 실제 동적 테스트를 거친 것도 아니고, 무엇보다 채점 기준을 만든 것도 채점을 한 것도 같은 AI입니다. 다만 방향 자체는 맞습니다 — 네트워크 모듈이 아예 없어서 정보 유출 경로가 원천 차단된다거나, `Process.Start` 같은 셸 호출이 없다는 건 코드베이스를 grep 한 번만 돌려봐도 확인되는 사실이라 신뢰도가 높은 항목이고요. "정성적으로 위험 요소가 별로 없는 로컬 데스크톱 앱"이라는 결론 자체엔 동의하지만, 그걸 "100%"라는 숫자로 포장하는 순간 실제보다 더 검증됐다는 착각을 주기 쉽다는 게 이번에 느낀 지점입니다.

## 느낀 점

`docs/` 폴더에는 기획서·설계서·분석서·보고서가 기능 하나당 세트로, 총 수십 개가 쌓였습니다. 문서화 자체는 꼼꼼했지만, 그 문서 두께와 실제 완성도가 항상 비례하지는 않았습니다. 렌더링 지연이나 빌드 에러처럼 "실제로 실행해봐야 보이는" 문제들은 결국 제가 쓰고 반응하는 과정을 몇 바퀴 더 거쳐야 잡혔습니다.

그래도 결과적으로는 설치까지 되는 실행 파일이 나왔다는 점에서, 코드를 직접 짜지 않고도 어느 정도 규모 있는 데스크톱 앱을 완성까지 끌고 갈 수 있다는 건 확인한 셈입니다. 다만 "일치율 100%", "보안 100%" 같은 AI가 스스로 매긴 숫자는 참고 지표 정도로만 보고, 실제 검증(빌드 통과, 기능 동작 확인, 필요하면 사람이 보는 보안 리뷰)은 따로 챙겨야 한다는 게 이번 프로젝트의 결론입니다.
